# Phase 3: assessments and BKT adaptation

**Outcome (2026-11-02):** `ADAPTIVE_TUTORING_IMPLEMENTED_PENDING_APPROVAL`. The pure BKT,
observation-semantics and adaptive-policy modules, the typed decision records, issued cue
snapshots, a new assessment type, deterministic traces, an exact-rational reference
comparison, sensitivity evidence and local browser journeys are implemented and pass.
Every production learning policy (BKT-001 to BKT-005), the task-to-KC mapping (EDU-002)
and the learner direction tolerance (IMP-012) still need named approval, so real-data
lessons run `NON_ADAPTIVE` and record an explicit no-op per attempt. Adaptive behaviour
runs only on the visibly synthetic technical fixture.

Specification: `TUTORING_BKT_SPEC.md`, ADR-005, IMP-012/013/014/016/019. Literature:
the "Learner-modelling sources" section of `references/UFUQ_SOURCE_REGISTER.md`.

## What exists

### `packages/tutoring-core` (pure, no dependencies)

| Module | Responsibility |
|---|---|
| `vocabulary.ts` | KC-01..KC-05 names, scaffold states, session purposes, configuration statuses, the typed `ModelUpdateInstruction`. No value. |
| `bkt/model.ts` | Parameter validation (finite, in [0,1], 1-S > G), the observation posterior, one learning transition, `applyModelDecision` with typed `OBSERVATION` / `TRANSITION_ONLY` / `NO_MODEL_UPDATE` records, the stale-revision and model-chain guards, and the threshold classifier with an explicit boundary rule. |
| `bkt/analysis.ts` | Sequences, attempts to threshold, exact false-mastery probability, recovery after errors, transition-caused crossings and the DEV-008 lower fixed point. |
| `observations/` | The ordered observation-rule table, a validator that proves it total over 4 purposes x 3 states x 7 response statuses x 3 attempt kinds (252 cells), and the decision function. It also holds independent-confirmation counting. |
| `adaptive-policy/` | The scaffold rule engine with allowed transitions only, the cue vocabulary with one fixed classification per cue, and the cue-configuration validator. |
| `learner-model.ts` | Composition: provisions all five KC rows at once; `processAttempt` returns one observation, one model and one scaffold decision; `replayAttempts` gives deterministic traces; `validateLearningConfiguration`. |

Invariants enforced in code, not left to configuration:

- Evaluation-only purposes (PRE_TEST, POST_TEST, RECALL) are always `NO_MODEL_UPDATE` and
  never change scaffolding (BKT-005 default; enabling them needs a new schema version and
  an approved protocol).
- Only a scored binary response can be an observation from the score. A measured
  direction without a tolerance (`SCORED_UNCLASSIFIED`) never is. Only no-response,
  timeout and abandonment may be treated as incorrect; an invalid attempt never is.
- Assistance comes only from the server-issued cue snapshot. Client telemetry and
  accessibility accommodations are carried separately and cannot change it.
- GUIDED moves only to FADING; FADING to GUIDED or INDEPENDENT; INDEPENDENT may restore
  FADING or GUIDED. Every transition needs evidence conditions with explicit inclusive or
  exclusive boundaries and a reason code. No input can request a state, and no "slip
  rate" exists (DEV-007).
- FADING issues no cue classified `DIRECT_TARGET_REVEAL`; INDEPENDENT issues none at all.
- Threshold status (`MEETS_THRESHOLD`) and independent confirmation are separate fields.
- A mastery chain is bound to its parameter-set and model versions; a mismatch is
  rejected, never continued. The API keys each chain by the configuration payload hash.

### Assessment types (`packages/assessment-core`)

| Task kind | Answer | Scoring |
|---|---|---|
| `IDENTIFY_PATTERN_MEMBER`, `IDENTIFY_TARGET_STAR` | one star handle | exact identity (Phase 2) |
| `SELECT_ALL_PATTERN_MEMBERS` (new) | a set of handles | exact set equality; unknown or repeated handles make the selection invalid; missing/extra counts are diagnostics only (no partial credit is approved) |
| `INDICATE_DIRECTION` | an azimuth | wrapped difference; graded only against an explicit tolerance policy on the direction record (inclusive boundary), otherwise `MEASURED_NO_TOLERANCE` |

`scoredOutcomeOf` hands the learner model `CORRECT`, `INCORRECT` or `UNCLASSIFIED`. The
answer types have no singular case: targets are horizontal and answers are azimuths of
horizontal directions.

### Data: the learning configuration artifact

`UFUQ_LEARNING_CONFIGURATION` envelopes are generated by `tools/catalogue` and approved
through `data/approvals/` like every other artifact (`npm run approvals:status` lists
`learning-configuration-v1`). `tools/catalogue` now depends inward on the pure
`tutoring-core` validators (a justified edge in `scripts/check-boundaries.mjs`).

| Artifact | Mode | Contents |
|---|---|---|
| `learning-configuration-v1` (`data/curation/tutoring/learning-configuration.v1.json`, `REVIEW_REQUIRED`) | `NON_ADAPTIVE` | The report's reproducible example parameters (L0 .20, T .10, G .20, S .10; `REPORT_EXAMPLE_NOT_CALIBRATED`) and the fixed Phase 2 presentation. Threshold, independent confirmation, observation policy and scaffold policy are null, each listed with its owning decision (BKT-001/003/004). |
| `synthetic-learning-configuration-v1` (`SYNTHETIC_TECHNICAL_FIXTURE`) | `ADAPTIVE` | The same example parameters plus invented technical policies chosen to exercise every decision kind and transition. They are not proposed learning policies. |

Content changes: each route step names one primary knowledge component
(`knowledgeComponentId`, validated so a route never credits one KC twice). The real
mapping is **proposed for EDU-002 review**: Banat Na'sh to KC-01; al-Kaff al-Khadib to
KC-02, because the same pattern record carries its Greco-Arabic name Dhat al-Kursi;
al-Jady to KC-03; True North to KC-04. KC-05 (Qibla) has no task yet. `DirectionTarget`
gained `learnerTolerance`; it is null in real content, and the validator refuses a real
tolerance without approved review. The synthetic direction carries an invented 10°
technical tolerance so the graded path is testable.

### API and contracts (`lesson.v2`, `/api/v2`)

- `lesson.v2` replaces `lesson.v1` (no released client depended on it). It adds the
  learner, the session purpose, the issued support (`mode`, `scaffoldState`,
  `cueSnapshotId`, `cueIds`), per-step overlays and hints, the `STAR_SET_SELECTION`
  answer, optional untrusted `clientTelemetry`, and a technical `trace` per attempt.
- The IMP-016 development fixture identity (`POST /api/v2/development-learners`, and
  `GET .../:learnerId/trace`) exists only when the server is composed with
  `enableDevelopmentIdentity` (`UFUQ_ENABLE_DEVELOPMENT_IDENTITY=1`). It is in memory with
  no personal data. Without it, lesson creation fails closed
  (`DEVELOPMENT_IDENTITY_DISABLED`). `npm run test:e2e` and `npm run preview:review` set
  it; production composition never does.
- Only `LEARNING` sessions can be created. Evaluation purposes return
  `SESSION_PURPOSE_NOT_ENABLED` until BKT-005 approves a protocol.
- Each step is issued with a fresh cue snapshot from the learner's current state for that
  KC. The scene shows exactly the issued cues. A partial guide is sent as a start star
  plus a server-computed midpoint direction, never the target handle, so a client cannot
  reveal the answer while support is fading.
- A submission issued against an older mastery revision is rejected before scoring with
  `409 STALE_MASTERY_REVISION` and a reissued step (spec: "a stale expected revision is
  rejected and reissued").
- An incorrect answer reissues the same step (attempt kind `RETRY_AFTER_FEEDBACK`).
  Correct and unclassified answers advance.

### Web

The start screen creates one development learner per tab, so support adapts across
lessons. The lesson view renders only the current step's issued overlays. It offers a
multi-select list with a submit button for the set task, shows the support level and
hints, and keeps a collapsed "Technical model trace (developers and reviewers; not
learner feedback)" panel. Raw probabilities and reason codes are not learner-facing
wording (BKT-003/004).

## What a reviewer approves, and how

1. **BKT-001 / DEV-006:** choose the assisted-evidence option and the handling of each
   response status and retry. Express it as an `observationPolicy` rule table; the
   validator proves it total.
2. **BKT-002:** parameters (global or per KC), admissible region and migration. Replace
   the report example set or mark it approved.
3. **BKT-003:** threshold value and boundary rule, independent-success count, and
   learner wording.
4. **BKT-004:** initial scaffold, transition rules, cue lists per KC and state, and
   learner-facing explanations. Express them as `scaffoldPolicy` and an `ADAPTIVE`
   `cueConfiguration`.
5. **BKT-005:** session-purpose protocol before any PRE_TEST, POST_TEST or RECALL lesson.
6. **EDU-002:** the proposed step-to-KC mapping in `data/curation/routes/routes.v1.json`.
7. **IMP-012:** a learner direction tolerance on `direction-true-north`.

Edit `data/curation/tutoring/learning-configuration.v1.json`, run `npm run data:generate`,
then record the approval in `data/approvals/learning-configuration-v1.approval.v1.json`
(see `data/approvals/README.md`). The generator rejects an invalid or incomplete
configuration and a stale approval.

## Known limitations for review

- The accessible star list shows every star's altitude and azimuth in every scaffold
  state (a Phase 2 accessibility equivalent). It therefore acts as an orientation cue
  even in INDEPENDENT: the near-pole target is the low star near azimuth 0. Whether the
  list counts as an accommodation or a cue, and how an accessible INDEPENDENT task should
  look, is for BKT-004 and the EDU-002 accommodation review. The code does not change
  accessibility behaviour on its own.
- Visual checks on 2026-11-02 confirmed that GUIDED step 2 draws the helper outline and
  the full guide to the target, and that FADING draws the outline and only the first
  half of the guide.

## Not in Phase 3

Durable persistence, the idempotent attempt transaction, duplicate-request replay and
real authentication are Phase 4 (IMP-015/016/017). Timer-based `TIMEOUT`, `NO_RESPONSE`
and `ABANDONED` statuses exist in the vocabulary and policies but are not produced by the
API yet. Qibla (KC-05) needs the Qibla geodesy decisions first.
